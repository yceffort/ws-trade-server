# M3: 부하 실험 도구

## 목표

gateway에 연결을 많이 붙이고 체결을 흘려서 글에 쓸 숫자를 얻는다. 알고 싶은 것은 네 가지다.

1. 연결 수가 늘면 gateway의 메모리와 CPU, 전달 지연이 어떻게 변하는가
2. 읽지 않는 클라이언트가 섞여 있으면 그 연결만 끊기고 나머지는 영향이 없는가
3. 링을 읽는 간격(`--poll-us`)이 지연에 얼마나 더해지는가
4. 그 과정에서 순번이 빠지거나 예상 밖으로 끊기는 연결이 있는가

이번 작업은 **측정 도구를 만드는 것까지**다. 큰 규모의 실행과 결과 해석은 컨트롤러가 한다. gateway의 동작(`src/hub.rs`, `src/connection.rs`, `src/stomp.rs`, `src/ring.rs`, `src/bridge.rs`)은 바꾸지 않는다. 바꿔야 측정할 수 있다고 판단하면 멈춰서 보고한다.

## 먼저 읽을 것

`AGENTS.md`, `README.md`, `.agents/skills/rust-skills/SKILL.md`에서 `async-`, `perf-`, `err-` 범주 중 해당하는 규칙, 그리고 현재 `src/`와 `tests/` 전체.

## 부하 발생기 (`src/bin/loadgen.rs`, 필요하면 `src/loadgen.rs`)

한 프로세스가 **체결을 링에 쓰는 일**과 **클라이언트 N개가 받는 일**을 같이 한다. 같은 프로세스의 시계로 "쓴 시각"과 "받은 시각"을 재기 위해서다. 실제 `feed`와 동시에 띄우지 않는다(링의 쓰는 쪽은 하나다).

### 인자

| 인자 | 기본값 | 뜻 |
| --- | --- | --- |
| `--url` | `ws://127.0.0.1:8080/ws` | gateway 주소 |
| `--ring` | feed와 같은 기본 경로 | 쓸 링 파일 |
| `--connections` | 100 | 클라이언트 수 |
| `--symbols` | feed와 같은 기본 3종목 | 쓸 종목. 모든 클라이언트가 이 종목 전부를 구독한다 |
| `--rate` | 5 | 종목당 초당 평균 체결 수 |
| `--stalled` | 0 | 구독만 하고 전혀 읽지 않는 클라이언트 수(`--connections`에 포함) |
| `--probes` | 50 | 지연을 재는 클라이언트 수 |
| `--warmup` | 3 | 연결을 다 붙인 뒤 측정 전에 기다리는 초 |
| `--seconds` | 20 | 측정 시간(초) |
| `--out` | 표준 출력 | 결과 JSON을 쓸 파일 |

### 동작 순서

1. 링의 쓰는 쪽을 연다.
2. 클라이언트를 붙인다. 한꺼번에 열지 말고 200개씩 묶어 차례로 연다. 각 클라이언트는 핸드셰이크(`v12.stomp`), `CONNECT`(`connection-id`는 클라이언트마다 다르게), 종목마다 `SUBSCRIBE`(`receipt` 포함)를 보내고 모든 `RECEIPT`를 받으면 준비된 것으로 본다. 붙이는 데 걸린 시간과 실패 수를 센다.
3. 전부 준비되면 체결을 쓰기 시작하고 `--warmup` 동안 측정 없이 흘린다.
4. `--seconds` 동안 측정한다.
5. 체결 쓰기를 멈추고, 1초 더 받은 뒤, 결과를 쓰고 끝낸다.

### 클라이언트 종류

- **일반**: 프레임을 받아 `MESSAGE` 수를 세고, `message-id`의 순번이 1부터 빠짐없이 이어지는지 확인한다. 본문은 파싱하지 않는다. 5초마다 heartbeat(`\n`)를 보낸다.
- **탐침**(`--probes`개): 일반 클라이언트가 하는 일에 더해 본문을 파싱해서 지연을 잰다.
- **멈춘 클라이언트**(`--stalled`개): 구독까지 마친 뒤 소켓에서 아무것도 읽지 않는다. 측정이 끝날 때 서버가 그 연결을 끊었는지(읽어 보면 EOF나 오류가 나는지) 확인하고, 끊긴 수를 센다.

### 지연 재는 법

체결을 링에 쓰기 직전에 `(종목, cumulative_volume)`을 키로 `Instant`를 기록한다. `cumulative_volume`은 종목 안에서 계속 늘기 때문에 키가 겹치지 않는다. 탐침은 받은 본문의 `code`와 `cumulativeVolume`으로 그 시각을 찾아 "받은 시각 - 쓴 시각"을 지연으로 기록한다. 기록은 측정 구간의 것만 쓴다. 지연은 마이크로초 단위로 모아 p50, p90, p99, max를 낸다. 평균만 내지 않는다.

### 결과 JSON

한 번 실행에 객체 하나. 최소한 다음을 담는다.

- 실행 조건: 인자 전부
- 붙이기: 성공 수, 실패 수, 걸린 밀리초
- 쓴 체결 수, 측정 구간의 초당 체결 수
- 받은 `MESSAGE` 총수와 측정 구간의 초당 수, 기대치(체결 수 × 준비된 일반 클라이언트 수) 대비 비율
- 순번이 빠진 클라이언트 수
- 측정 중 예상 밖으로 끊긴 일반 클라이언트 수
- 멈춘 클라이언트 중 서버가 끊은 수
- 지연: 표본 수, p50, p90, p99, max(마이크로초)

gateway의 메모리와 CPU는 이 도구가 재지 않는다(아래 스크립트가 잰다).

## 실행 스크립트 (`bench/run.sh`)

한 조건을 처음부터 끝까지 돌린다. 인자는 loadgen 인자를 그대로 넘기고, `--poll-us`만 gateway로 보낸다.

1. `ulimit -n`을 올린다(올리지 못하면 이유를 출력하고 끝낸다).
2. 임시 링 경로를 정하고 릴리스 빌드한 `gateway`를 임의의 빈 포트로 띄운다.
3. `loadgen`을 띄운다.
4. loadgen이 도는 동안 1초마다 gateway의 RSS(KB)와 CPU(%)를 `ps`로 읽어 모은다.
5. 끝나면 gateway를 종료하고, loadgen의 결과 JSON에 gateway의 RSS(측정 구간 최댓값)와 CPU(측정 구간 평균과 최댓값), 그리고 실행 환경(OS, CPU 모델, 코어 수, `rustc --version`, 저장소에 커밋이 있으면 커밋 해시)을 합쳐 `bench/results/<이름>.json`으로 쓴다.
6. 어떤 경우에도 gateway 프로세스와 임시 링 파일을 남기지 않는다(`trap`).

`bench/README.md`에 사용법과 결과 필드의 뜻을 짧게 적는다. `bench/results/`는 커밋 대상이다(결과가 글의 근거다).

## 테스트 (필수)

1. 통합 테스트: 테스트 안에서 gateway를 임시 링으로 띄우고 `loadgen` 실행 파일을 연결 20개, 탐침 5개, 멈춘 클라이언트 0개, 워밍업 1초, 측정 2초로 돌린다. 결과 JSON에서 붙이기 실패 0, 순번 빠짐 0, 받은 수 > 0, 지연 표본 > 0, p50 ≤ p99 ≤ max를 확인한다.
2. 통합 테스트: 송신 큐를 작게 잡은 gateway에 멈춘 클라이언트 3개를 섞어 돌리면 끊긴 수가 3이고 나머지 클라이언트의 순번 빠짐이 0이다. 멈춘 클라이언트가 실제로 끊기려면 그 연결의 큐가 차야 하므로, 이 테스트에서는 체결을 충분히 빠르게 쓴다.
3. 지연 통계(백분위 계산)의 단위 테스트.
4. 기존 테스트 31개는 계속 통과한다.

`bench/run.sh`는 연결 200개, 측정 5초로 한 번 직접 돌려 결과 파일이 만들어지는지 확인하고, 그 결과 파일은 지운다.

## 규칙

- git으로 상태를 바꾸지 않는다. `cargo +<toolchain>`이나 `rustup` 명령을 쓰지 않는다. 도구를 설치하지 않는다.
- 이 문서, `docs/`, `proto/`, `contract/`, `capture/`, `evidence/`, `.agents/`, `.claude/`, `AGENTS.md`, `CLAUDE.md`는 수정하지 않는다.
- 파일 하나가 250줄을 넘어가면 멈추고 보고한다.
- 큰 규모(연결 1000개 초과)로 돌리지 않는다. 그것은 컨트롤러가 한다.
- 프로세스와 임시 파일을 남기지 않는다.
- `README.md`에 "부하 실험" 절을 추가해 `bench/run.sh` 사용법 한 줄과 `bench/README.md`로 가는 안내만 적는다.
