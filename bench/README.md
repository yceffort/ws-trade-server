# 부하 실험

인증과 WSS, 재접속, 거절 및 정리 동작을 함께 확인하는 반복 실행은 [복합 수명 검증](soak/README.md)을 따른다. 이 시나리오는 아래 지연 및 전달률 측정과 별도로 실행한다.

gateway에 연결을 많이 붙이고 체결을 흘려서 메모리, CPU, 전달 지연을 잰다. `loadgen`이 체결을 링에 쓰는 일과 클라이언트 N개가 받는 일을 한 프로세스에서 같이 하므로, 같은 시계로 "쓴 시각"과 "받은 시각"을 잴 수 있다. 실제 `feed`와 동시에 띄우지 않는다(링의 쓰는 쪽은 하나다).

## 사용법

```sh
bench/run.sh <이름> [--poll-us N] [--latest-first-topics 목록] [--latest-first-depth K] [--metrics] [loadgen 인자...]
bench/run.sh conn-1000 --connections 1000 --probes 50 --seconds 20
bench/run.sh poll-1000us --poll-us 1000 --connections 200
```

`--latest-first-topics`와 `--latest-first-depth`는 gateway에 그대로 넘기고 결과의 `gateway.args`에 남긴다. `--metrics`를 주면 gateway가 loopback 조회 포트(`--http-addr 127.0.0.1:0`)를 열고, 스크립트는 loadgen이 끝난 뒤 `GET /metrics`를 한 번 읽어 결과에 넣는다. 셋 다 주지 않으면 이 인자를 넣기 전과 똑같이 돈다.

스크립트는 `ulimit -n`을 올리고, 릴리스 빌드한 `gateway`를 임시 링과 빈 포트로 띄우고, `loadgen`을 돌리면서 1초마다 gateway의 RSS와 CPU를 `ps`로 읽고, 끝나면 결과를 `bench/results/<이름>.json`에 쓴다. gateway와 임시 파일은 어떤 경우에도 남기지 않는다. `jq`가 필요하다. `--url`, `--ring`, `--out`은 스크립트가 정하므로 넘기지 않는다.

Linux에서 재려면 `bench/linux.sh`로 같은 명령을 컨테이너 안에서 돌린다(Docker 필요). gateway는 코어 0-3, loadgen은 4-9에 `taskset`으로 고정하고, 바꾸려면 `GATEWAY_CPUS`, `LOADGEN_CPUS`를 준다. 고정한 코어는 결과의 `environment`에 남는다.

```sh
bench/linux.sh bench/run.sh linux-conn-1000 --connections 1000
GATEWAY_CPUS=0-1 LOADGEN_CPUS=2-9 bench/linux.sh bench/run.sh linux-conn-1000-2core --connections 1000
```

`loadgen`을 직접 쓸 때는 gateway를 먼저 띄우고 같은 `--ring`을 준다. 워밍업은 1초 이상으로 둔다. gateway의 링 브리지는 링 파일이 생긴 뒤 최대 0.5초 늦게 열고 열린 시점의 끝에서부터 읽으므로, 워밍업이 짧으면 처음 체결이 전달되지 않아 `delivery.ratio`가 1보다 작아진다.

| 인자 | 기본값 | 뜻 |
| --- | --- | --- |
| `--url` | `ws://127.0.0.1:8080/ws` | gateway 주소 |
| `--ring` | feed와 같은 기본 경로 | 쓸 링 파일 |
| `--connections` | 100 | 클라이언트 수 |
| `--symbols` | feed와 같은 3종목 | 쓸 종목. 모든 클라이언트가 전부 구독한다. 종목 코드는 서로 달라야 한다(받은 체결을 코드로 쓴 기록과 짝짓는다) |
| `--rate` | 5 | 종목당 초당 평균 체결 수 |
| `--stalled` | 0 | 구독만 하고 읽지 않는 클라이언트 수(`--connections`에 포함) |
| `--probes` | 50 | 지연을 재는 클라이언트 수(`--connections`에 포함) |
| `--warmup` | 3 | 연결을 다 붙인 뒤 측정 전에 흘리는 초 |
| `--seconds` | 20 | 측정 시간(초) |
| `--out` | 표준 출력 | 결과 JSON 파일 |

연결은 200개씩 묶어 차례로 연다. 일반 클라이언트는 `message-id`의 순번이 1부터 빠짐없이 이어지는지 보고, 탐침은 거기에 더해 본문을 파싱해 지연을 잰다. 멈춘 클라이언트는 측정이 끝날 때 소켓을 읽어 보고, 쌓인 데이터를 비운 뒤 EOF나 오류가 나면 서버가 끊은 것으로 센다.

## CI에서 돌리기

`.github/workflows/bench.yml`이 서버나 측정 도구를 건드린 PR마다, 그리고 Actions 탭에서 직접 실행할 때 `bench/ci.sh`를 돌린다. 조건은 둘이고 각각 10초씩 세 번 돌려 실행별 값과 중앙값을 실행 요약에 표로 적는다. PR이면 기준 브랜치도 같은 러너에 받아 번갈아 돌려 나란히 적는다.

| 조건 | 연결 | 종목당 초당 건수 | 보는 것 |
| --- | --- | --- | --- |
| `steady` | 1,000 | 10 | gateway가 여유 있을 때의 지연 |
| `saturated` | 2,000 | 20 | 코어 하나가 꽉 찼을 때 초당 몇 프레임을 보내는가 |

조건의 이름은 2코어 러너 기준이다. gateway와 loadgen에 코어를 하나씩 주면 `saturated`에서 gateway 코어가 100%가 되고 지연이 초 단위로 밀린다(2026-11-20 첫 실행에서 초당 약 11만 프레임). 코어가 많은 기계에서는 같은 조건이 포화에 이르지 않는다.

공용 러너는 이웃의 부하에 따라 값이 흔들리므로 지연과 처리량은 실패 조건이 아니다. 같은 실행 안의 기준 값과만 견준다. 실패 조건은 전달이 온전한지다. 모든 실행에서 연결 실패, 순번 빠짐, 예상 밖 끊김, 짝 없는 표본이 0이어야 하고, `steady`에서는 `delivery.ratio`가 1이어야 한다. 결과 JSON은 `bench-results` 아티팩트로 남는다.

로컬에서도 같은 스크립트를 쓸 수 있다. 횟수, 시간, 조건은 환경 변수로 바꾼다.

```sh
bench/ci.sh                                   # 지금 코드만
bench/ci.sh ../ws-trade-server-main           # 기준 체크아웃과 번갈아
BENCH_ROUNDS=2 BENCH_SECONDS=5 BENCH_SCENARIOS="steady:500:5" bench/ci.sh
```

## 지연을 재는 법

체결을 링에 쓰기 직전에 `(종목, cumulative_volume)`별로 `Instant`를 기록하고, 탐침은 프레임을 읽은 직후에 `Instant`를 찍은 뒤에야 본문을 파싱한다. 둘을 짝짓는 일은 실행이 끝난 뒤에 한다(실행 중에는 잠금도 조회도 없다). 쓴 시각이 측정 구간 안인 표본만 지연으로 세고, 구간 밖이거나 짝이 없는 표본은 버리지 않고 건수로 남긴다. 백분위는 nearest-rank 방식이다. 오름차순 n개에서 p백분위는 `ceil(p/100 * n)`번째 값이라 표본이 적으면 p99가 max와 같아진다.

받은 시각은 클라이언트 태스크가 깨어나 프레임을 읽는 시각이다. 연결 수가 코어 수보다 훨씬 많으면 loadgen 자신의 스케줄링 지연이 지연에 섞이고, loadgen과 gateway가 같은 기계의 코어를 나눠 쓴다.

## 결과 필드

`delivery`가 없는 결과 파일은 이 필드를 넣기 전에 만든 것이다. 거기 있는 `messages.expected`, `messages.ratio`는 받은 시각으로 센 수를 나눈 값이라 빠진 체결이 없어도 1을 넘을 수 있다.

| 필드 | 뜻 |
| --- | --- |
| `config` | 실행 조건. loadgen 인자 전부(종목은 topic으로 적는다) |
| `connect.ready`, `connect.failed`, `connect.millis` | 준비된 연결 수, 실패 수, 전부 붙이는 데 걸린 밀리초 |
| `clients.normal`, `clients.probes`, `clients.stalled` | 준비된 클라이언트 수(역할별) |
| `written.total` | 링에 쓴 체결 수(워밍업 포함) |
| `written.measured`, `written.per_sec` | 측정 구간에 쓴 체결 수와 초당 수 |
| `messages.total` | 받은 `MESSAGE` 총수(워밍업 포함, 멈춘 클라이언트 제외) |
| `messages.measured`, `messages.per_sec` | 측정 구간에 받은 수와 초당 수. 받은 시각으로 세므로 쓴 수와 견주지 않는다 |
| `delivery.expected` | 기대치. `written.measured` x 탐침 수 |
| `delivery.delivered` | 측정 구간에 쓴 체결을 탐침이 받은 수. 쓴 기록과 짝지어 세므로 워밍업 때 쓴 체결과 측정이 끝난 뒤에 쓴 체결은 넣지 않는다 |
| `delivery.ratio` | `delivered` / `expected`. 빠진 체결이 없으면 1이다. 마지막 1초 안에 도착하지 못한 체결은 빠진 것으로 센다. 탐침이 없으면 null |
| `seq_gap_clients` | `message-id` 순번이 1부터 빠짐없이 이어지지 않은 클라이언트 수 |
| `unexpected_disconnects` | 준비된 뒤 서버가 끊은 일반 클라이언트 수(탐침 포함) |
| `stalled_kicked` | 서버가 끊은 멈춘 클라이언트 수 |
| `latency_us.samples` | 지연 표본 수 |
| `latency_us.p50`, `p90`, `p99`, `max` | 지연(마이크로초). 표본이 없으면 null |
| `latency_us.unmatched` | 쓴 기록과 짝이 없는 표본 수. 0이 아니면 이 도구나 링을 의심한다 |
| `latency_us.unparsed` | 본문을 읽지 못한 표본 수 |
| `latency_us.outside_window` | 쓴 시각이 측정 구간 밖이라 뺀 표본 수 |
| `gateway.poll_us` | gateway의 `--poll-us` |
| `gateway.rss_kb_idle` | 연결을 붙이기 전 gateway의 RSS(KB) |
| `gateway.rss_kb_max` | 측정 구간의 RSS 최댓값(KB) |
| `gateway.cpu_pct_mean`, `cpu_pct_max` | 측정 구간 `ps %cpu`의 평균과 최댓값. `ps`의 값은 구간 값이 아니라(macOS는 감쇠 평균, Linux는 프로세스 수명 평균) 앞 구간의 부하가 섞인다 |
| `gateway.cpu_pct_from_time` | 측정 구간 첫 표본과 끝 표본 사이 누적 CPU 시간의 증가분을 경과 시간으로 나눈 값 |
| `gateway.samples` | 측정 구간 안의 `ps` 표본 수 |
| `gateway.args` | gateway에 넘긴 최신 우선 정책 인자. 넘기지 않았으면 필드가 없다 |
| `gateway.metrics` | `--metrics`를 줬을 때 loadgen이 끝난 뒤 읽은 gateway의 `GET /metrics`. 워밍업과 마지막 1초를 포함한 누적값이다 |
| `environment` | OS, CPU 모델, 코어 수, `rustc --version`, 커밋 해시(커밋이 없으면 null), `gateway_cpus`와 `loadgen_cpus`(코어를 고정하지 않았으면 null) |

`slow-policy-off-*.json`과 `slow-policy-on-*.json`은 이 스크립트가 조회 포트를 늘 열던 때에 만들었다. 그래서 두 정책 모두 `gateway.metrics`가 있고, 넘긴 topic은 `gateway.args` 대신 `gateway.latest_first_topics`에 있다.

CPU는 코어 하나를 100으로 센다. 측정 구간이 짧으면 표본이 몇 개뿐이므로 `gateway.samples`를 함께 본다.

## macOS 루프백 결과를 읽을 때

연결 5,000개 이상의 결과에는 gateway가 아니라 측정 환경의 한계가 섞여 있다. 클라이언트와 서버가 같은 기계에 있으면 연결 하나가 소켓 두 개를 쓰고, 그 버퍼가 모두 한 커널의 네트워크 메모리에서 나온다. 2026-11-19에 연결 10,000개 조건(Apple M5, macOS)에서 확인한 것은 다음과 같다.

- gateway 워커 스레드 10개의 호출 스택을 `sample`로 5초 동안 뜨면 스레드마다 표본의 78~100%가 `sendto` 안이다. 같은 조건에서 gateway가 쓴 CPU는 코어 1개 안팎이고, loadgen 워커는 표본의 약 75%가 대기 상태였다.
- 한 실행에서 `netstat -m`의 `requests for memory denied`가 2,090,227 늘었다. 연결 1,000개와 5,000개 실행에서는 늘지 않았다. 연결 5,000개 실행 중간에는 네트워크 메모리의 41.3%가 쓰이고 있었다.
- 그 실행은 20초짜리 측정이 15분 넘게 걸렸다.

그래서 `conn-10000*.json`의 지연은 서버 설계의 수치로 쓰지 않는다. 같은 조건을 Linux에서 재면(`linux-conn-10000.json`) p50 14.7ms, p99 41.5ms이고 세 번 돌려 p50이 14.7~15.0ms였다. 그때 gateway 워커 4개는 CPU를 24%씩 고르게 썼고 `/proc/net/sockstat`의 TCP 메모리는 226쪽이었다.

결과를 비교하기 전에 `connect.failed`가 0인지, `written.per_sec`가 조건(종목 수 x `--rate`)과 맞는지 먼저 본다. 둘 중 하나라도 어긋난 실행은 버린다.

## Linux 결과를 읽을 때

`linux-*.json`은 같은 기계(Apple M5)의 OrbStack 가상 머신(Linux 7.0.14, aarch64, 10코어)에서 쟀다. 클라이언트와 서버가 한 커널에 있다는 점은 macOS 측정과 같다.

이 가상 머신에서는 짧은 sleep이 요청한 만큼 자지 않는다. 50us, 200us, 1000us를 요청하면 모두 약 3ms(최대 4.5ms)를 잔다(같은 측정이 macOS에서는 79us, 304us, 1512us). 그래서 `--poll-us`가 0이 아닌 결과에는 링을 읽기까지의 대기가 0~4.5ms 섞이고, `linux-poll-50`, `linux-poll-200`, `linux-poll-1000`은 서로 구별되지 않는다. 링 대기를 뺀 전달 지연은 `--poll-us 0`으로 잰 `linux-conn-*-poll0.json`에 있다. 이때 gateway의 코어 하나는 링을 읽는 스레드가 계속 쓴다.

## 쓰기 묶음

gateway의 연결 태스크는 송신 큐에 이미 쌓여 있는 프레임을 4개까지 쓰기 버퍼에 모은 뒤 소켓에 한 번만 쓴다(`src/connection/batch.rs`). 그 전에는 프레임마다 한 번씩 썼다. 아래는 묶기 전(`linux-batch-off-*.json`)과 뒤(`linux-batch-4-*.json`)를 `bench/ci.sh`로 같은 가상 머신에서 번갈아 10초씩 세 번 돌린 중앙값이다(2026-11-20, 연결 10,000개, gateway 코어 0-3, loadgen 코어 4-9, `--poll-us 200`).

| 종목당 초당 건수 | 보낼 프레임/초 | p50 ms | p99 ms | gateway CPU % | RSS MB | 받은 프레임/초 | 끊긴 연결 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 5 | 15만 | 16.9 → 17.7 | 44.9 → 45.7 | 104 → 113 | 142 → 150 | 14.7만 → 15.6만 | 0 → 0 |
| 40 | 120만 | 25.8 → 20.5 | 70.4 → 51.6 | 355 → 340 | 141 → 166 | 117만 → 120만 | 0 → 0 |
| 80 | 240만 | 242 → 48.8 | 494 → 155 | 399 → 389 | 168 → 167 | 239만 → 242만 | 0 → 0 |
| 120 | 360만 | 1,882 → 613 | 3,940 → 1,398 | 392 → 391 | 521 → 274 | 266만 → 341만 | 413~1,582 → 0 |

초당 5건에서는 큐에 프레임이 하나씩만 있어 묶을 것이 없다. 그 줄의 차이는 잡음이다. 같은 코드를 양쪽에 두고 돌려도 p50이 17.2ms와 17.8ms, CPU가 103~119%로 흔들렸다. 초당 40건부터 프레임이 큐에 쌓이고, 상한을 16으로 두고 세어 보면 쓰기 한 번에 평균 2.3개(초당 80건에서는 5.1개)가 나갔다. 초당 120건은 4코어가 감당하지 못하는 부하다. 묶기 전에는 송신 큐가 넘친 연결이 실행마다 413~1,582개 끊겼고, 묶은 뒤에는 끊긴 연결이 없었다.

쓰기 횟수가 절반쯤으로 줄어도 CPU는 4%쯤만 준다. `perf`로 보면 gateway CPU의 46~50%가 커널의 TCP 경로이고, 나머지는 비동기 런타임과 웹소켓 라이브러리에 함수마다 4% 미만으로 흩어져 있다. 그래서 초당 5건처럼 묶을 것이 없는 부하의 지연은 이 변경으로 줄지 않는다.

상한을 4로 둔 것은 메모리 때문이다. 웹소켓 라이브러리의 쓰기 버퍼는 한번 커지면 줄지 않아서 묶은 만큼의 메모리가 연결마다 남는다. 상한 16(`linux-batch-16-*.json`)과 4(`linux-batch-4r-*.json`)를 같은 방법으로 번갈아 재면 초당 80건에서 p50은 25.5ms 대 57.3ms로 16이 낮지만 RSS가 219MB 대 173MB로 46MB 더 들고, 초당 40건에서는 p50 19.1ms 대 22.1ms에 RSS 199MB 대 166MB였다.

이 표의 값은 같은 기계에서 다른 빌드와 테스트가 함께 돌던 때에 잰 것이다. 절대값보다 같은 줄의 앞뒤 차이를 본다. 결과 파일의 `environment.commit`은 null이다. 저장소를 git worktree로 받아 컨테이너에 물리면 그 안에서 저장소를 읽지 못한다. `off`와 `4`는 `feat/27-logging`의 28a4e54에 `bench/run.sh`의 포트 읽기 수정을 얹은 코드와, 거기에 쓰기 묶음을 더한 코드다. `16`과 `4r`은 그 바로 앞 커밋인 ee996ae에서 같은 변경의 상한만 바꿔 잰 것이다(두 커밋의 차이는 문서 하나다).

## 느린 수신자 정책 세 방식 비교

송신 큐가 찬 연결을 다루는 세 방식을 `examples/slow_policy.rs` 하나에서 같은 조건으로 견준다. 지금 방식은 본체와 같은 크기 제한 mpsc 큐이고 차면 연결을 끊는다. (가) 덮어쓰는 고리는 큐가 차면 가장 오래된, 버려도 되는 MESSAGE 하나를 빼고 새 것을 넣는다. (나) 구독별 최신 한 칸은 구독마다 대기 중인 MESSAGE를 한 건만 두고, 칸이 비어 있다가 채워질 때만 기존 mpsc 큐에 표지를 넣는다.

두 후보 모두 최신 우선 topic의 MESSAGE만 버린다. RECEIPT, ERROR, 끊기 정책 topic의 MESSAGE는 버리지 않고, 그런 항목만으로 큐가 차면 지금처럼 끊는다.

본체에는 (나)를 넣었다. `--latest-first-topics`로 고른 topic에만 쓰는 선택 정책이고, 기본값은 지금 방식(끊기)이다. 멈췄다 풀린 연결이 구독마다 가장 최근 체결을 바로 받고 한산한 구독의 최신분도 잃지 않은 것은 (나)뿐이었다. 멈춘 연결 하나가 붙드는 메모리도 (가)의 303,104B에 비해 672B였다.

대가는 쓰는 쪽이 조금만 밀려도 체결을 합친다는 것이다. 아래 "실제 gateway에서"의 측정에서는 읽기를 늦추지 않은 연결도 종목당 초당 5건에서 0.5~3.8%, 80건에서 7.1~19.0%를 잃었다. 그래서 본체는 송신 큐에 K건까지는 지금 방식처럼 쌓고, 그보다 깊을 때만 칸으로 접는다(아래 "깊이 K를 둔 (나)").

```sh
cargo run --release --example slow_policy
```

소켓과 웹소켓 라이브러리는 거치지 않는다. 예제 안의 축소판 hub가 본체 hub(`src/hub/state.rs`)의 색인과 팬아웃을 옮기고 송신 큐만 바꾼다. 연결마다 tokio 태스크 하나가 자기 큐에서 꺼내고, 본문을 손에 쥔 시점을 전달 완료로 본다. 본문은 248바이트다. `boundary_cost` 예제가 출력하는 국내 체결 STOMP 프레임은 370바이트이고 헤더를 빼면 본문이 246바이트다. 정상 경로에는 같은 측정을 본체 `Hub`로 한 줄을 함께 두어 축소판이 본체와 비용이 같은지 견준다.

2026-11-20에 Apple M5(Super 코어 4개, Efficiency 코어 6개), macOS 27.2.1(26B131), rustc 1.95.0, tokio 런타임 워커 10개로 쟀다. 예제를 세 번 실행해 중앙값을 적고, 괄호 안에 세 실행의 최소~최대를 적는다. 다른 프로그램이 함께 돌던 기계라 실행 전후 load average가 4.0~5.1이었다. 한 번 실행하는 데 4분 20초쯤 걸린다.

### 멈춘 수신자

연결 하나가 hot과 quiet 두 topic을 구독한 뒤 꺼내지 않는다. quiet은 측정 전에 한 번만 발행하고, 그 뒤 hot을 정상 경로와 같은 건수(워밍업 20건을 더해 5,020건, 2,020건) 발행하면서 나머지 연결의 지연을 잰다. 다 발행하면 멈춘 연결을 풀어 hot의 마지막 발행분을 받을 때까지, 끊겼으면 큐가 빌 때까지 꺼낸다. 발행 번호는 0부터 센다.

### 늦추는 수신자가 없을 때

연결 10,000개가 종목 3개를 모두 구독하고 쓰는 쪽은 꺼내기만 한다. 종목당 초당 5, 40, 80, 120건을 3초씩 발행하고 연결들이 받은 MESSAGE를 센다. 세 방식은 차례로 따로 돌린다. CPU는 발행하는 동안 프로세스가 쓴 코어 수다.

| 종목당 초당 | 받아야 할 건수 | 지금 유실 | (가) 유실 | (나) 유실 | CPU 코어 지금 / (가) / (나) |
| --- | --- | --- | --- | --- | --- |
| 5 | 26만~53만 | 0 | 0 | 0 | 1.1 / 1.1 / 1.2 |
| 40 | 329만~395만 | 0 | 0 | 세 실행 중 한 번 1건 | 1.8 / 1.9 / 2.0 |
| 80 | 685만~767만 | 0 | 0 | 세 실행 중 한 번 20,256건(0.30%) | 2.7 / 2.7 / 3.0 |
| 120 | 1,021만~1,155만 | 0 | 0 | 0 | 3.5 / 3.5 / 4.0 |

(나)가 이 조건에서 잃은 두 번의 원인은 확인하지 않았다. 구조상 (나)는 같은 구독의 다음 체결이 올 때까지 쓰는 태스크가 앞의 표지를 꺼내지 못했을 때만 버린다. 그래서 쓰는 태스크가 차례를 늦게 얻은 순간이 있었다고 추정한다.

실제 gateway는 소켓 쓰기와 링 브리지까지 거친다. 그 조건에서 잰 값은 아래 "실제 gateway에서"에 있고, 이 예제와 달리 느리지 않은 연결에서도 (나)가 체결을 합쳤다.

### 불변식 검사

용량 64인 큐 하나에 구독, 해지, 발행을 무작위로 4,000개 섞어 보내고, 끝에 x만 300건 더 보낸다. 구독과 해지는 절반이 receipt를 단다. topic은 최신 우선인 `/latest/x`(약 90%)와 `/latest/y`(3%), 끊기 정책인 `/strict`(1%)이고, 구독 id 세 개를 다시 쓴다. 수신단은 프레임 50개에 한 번꼴로 0~300us 멈칫해 큐를 채운다. 받은 순서로 아래를 검사하고, 어긋나면 예제가 assert로 멈춘다.

- 모든 MESSAGE는 발행 시점에 그 id로 살아 있던, 그 topic의 구독에 속한다. 한 구독 안에서 발행 순서가 바뀌거나 겹치지 않는다.
- 불변식 1: SUBSCRIBE의 RECEIPT가 그 구독의 첫 MESSAGE보다 먼저 나간다.
- 불변식 2: UNSUBSCRIBE의 RECEIPT 뒤에 그 구독의 MESSAGE가 나가지 않는다. 같은 id로 다시 구독할 때의 RECEIPT도 이전 구독에 대해 같은 규칙을 지킨다.
- 불변식 3: RECEIPT는 명령 순서대로 모두 나간다. 끊긴 라운드는 끊기기 전에 큐가 받아 둔 RECEIPT까지 빠짐없이 나왔는지 본다. 끊기지 않은 라운드에서는 `/strict`의 MESSAGE가 하나도 빠지지 않는다.
- 끝까지 살아 있는 최신 우선 구독이 그 topic의 마지막 발행분을 받았는지 센다. 불변식 7을 구독 단위로 본 것이다.

| 방식 | 라운드 | 끊긴 라운드 | 받은 프레임 | 버린 MESSAGE | 마지막 발행분을 못 받은 구독 |
| --- | --- | --- | --- | --- | --- |
| (가) | 50, 50, 50 | 0, 0, 0 | 37,186~43,137 | 94,023~100,866 | 10/57, 7/53, 7/62 |
| (나) | 50, 50, 50 | 1, 1, 1 | 23,780~26,716 | 110,465~113,812 | 0/41, 0/52, 0/57 |

세 실행 모두 assert에 걸리지 않았다. (가)에서는 끝까지 살아 있는 최신 우선 구독의 11~18%가 마지막 발행분을 받지 못했다. x가 고리를 채우는 동안 드물게 온 y의 마지막 건이 밀려난 것으로, 멈춘 수신자 표의 quiet과 같은 현상이다.

(나)의 끊긴 라운드는 버릴 수 없는 항목과 표지만으로 큐가 찬 경우다. 코드상 (나)의 큐에는 그 두 가지만 들어간다. 해지했거나 같은 id로 다시 구독해 끝난 구독의 표지도 꺼낼 때까지 큐 한 자리를 차지한다.

지금 방식은 이 검사에서 뺐다. 용량 64에서는 첫 멈칫에 끊겨 볼 것이 없고, 순서는 `src/hub/tests.rs`가 검사한다.

불변식 4의 `message-id` 순번은 이 예제에서 재지 않는다. 두 후보는 큐에 무엇이 들어가는지만 바꾸고, 순번은 지금처럼 `src/connection/batch.rs`가 실제로 쓰는 MESSAGE마다 매긴다. 그래서 건너뛴 체결은 번호를 받지 않는다. (나)에서 표지를 꺼냈는데 칸이 비어 있으면 MESSAGE 없이 넘어가야 하는데, 예제는 그때 `expect`로 멈추게 했고 위 실행에서 한 번도 멈추지 않았다.

### 실제 gateway에서

(나)를 본체에 넣은 뒤 `bench/run.sh`로 같은 조건을 기본 정책과 최신 우선 정책(loadgen의 세 topic 모두)에서 번갈아 세 번씩 쟀다. 연결 1,000개(탐침 50개), 종목 3개, 워밍업 3초, 측정 10초다. 2026-11-20에 같은 기계(Apple M5, macOS 27.2.1)에서 load average 1.8~3.9일 때 쟀다. 결과 파일은 `bench/results/slow-policy-{off,on}-{5,40,80}-{1,2,3}.json`이다.

탐침 유실은 측정 구간에 쓴 체결 가운데 탐침이 받지 못한 비율(1 - `delivery.ratio`)이다. 건너뜀은 gateway 전체에서 `latest_skipped_total`을, 큐에 넣은 MESSAGE 수와 그 값을 더한 수로 나눈 비율이다(워밍업과 마지막 1초를 포함한다). 세 실행의 값을 실행 순서대로 적는다. CPU는 측정 구간 `ps %cpu` 표본의 평균이다.

| --- | --- | --- | --- | --- | --- | --- | --- |
| 5 | 기본 | 0, 0, 0 | 0, 0, 0 | 5.2, 4.3, 4.3 | 11.6, 11.1, 13.4 | 32, 28, 26 | 0, 0, 0 |

기본 정책은 초당 80건의 첫 실행을 빼고 하나도 잃지 않았다. 그 실행은 지연이 초 단위로 밀리면서 송신 큐가 넘친 연결 19개가 끊겼고(loadgen이 센 예상 밖 끊김은 17개), 같은 회차의 최신 우선 실행도 지연이 가장 컸지만 끊긴 연결 없이 19.0%를 잃었다.

최신 우선 정책에서는 읽기를 늦추지 않은 loadgen 클라이언트도 체결을 잃었다. 초당 5건은 gateway CPU가 30% 안팎인 한가한 조건인데도 0.5~3.8%였다. 탐침 50개의 유실률과 연결 1,000개 전체의 건너뜀 비율은 비슷했지만, 결과 파일에 연결별 분포가 없어 유실이 연결 전체에 퍼졌는지 일부 연결에 몰렸는지는 알 수 없다.

`message-id` 순번이 빠진 클라이언트(`seq_gap_clients`)는 18번 모두 0이었다. 건너뛴 체결은 번호를 받지 않으므로 순번으로는 유실을 알 수 없다. `bench/ci.sh`의 실패 조건 가운데 `steady`에서 `delivery.ratio`가 1이어야 한다는 조건은 최신 우선 정책에서는 성립하지 않는다.

지연과 CPU에서 두 정책의 차이는 실행 사이의 흔들림보다 작았다. 합친 만큼 보낸 프레임은 줄었지만(초당 80건에서 측정 구간에 초당 받은 MESSAGE가 최신 우선 20.1만~23.0만, 기본 21.5만~24.2만) gateway CPU가 줄지는 않았다. `gateway.cpu_pct_from_time`은 세 실행(46.0, 3.3, 129.8)에서 같은 실행의 `ps` 표본 평균과 크게 달라 쓰지 않았고, 원인은 확인하지 않았다.

같은 종목의 다음 체결이 앞의 체결을 쓰기 전에 오면 합쳐진다. 종목당 초당 5건의 지수 분포 간격에서 다음 체결이 2ms 안에 올 확률은 약 1%다. 그러니 발행부터 쓰는 쪽이 표지를 꺼내기까지 gateway 안에서 1~몇 ms가 걸리면 이 정도 유실이 나온다고 본다. 이 대기 시간은 따로 재지 않았다.

### 깊이 K를 둔 (나)

위의 실제 gateway 측정에서 (나)는 느리지 않은 연결의 체결까지 걸러 냈다. 그래서 본체의 최신 우선 정책은 큐 깊이 K(`--latest-first-depth`, 기본값 64)를 둔다. 발행이 오면 칸이 차 있을 때(표지가 큐에 있을 때)는 깊이와 상관없이 칸의 값만 바꾼다. 칸이 비어 있고 송신 큐에 K건 미만이 쌓여 있으면 일반 MESSAGE로 넣고, K건 이상이면 칸을 채우고 표지를 넣는다. K=0이면 위의 (나)와 같다. 예제에서는 `DepthTx<K>`가 같은 규칙이다.

깊이는 송신단의 `max_capacity() - capacity()`로 읽는다. tokio 1.54.1의 `Sender::capacity`는 보내거나 자리를 예약할 때 줄고 수신단이 꺼낼 때 늘어나며, hub는 예약을 쓰지 않는다. 그래서 이 값은 쓰는 태스크가 아직 꺼내지 않은 항목 수다. 쓰는 태스크가 묶어 쓰려고 이미 꺼낸 프레임은 들어가지 않는다.

칸이 차 있으면 무조건 값만 바꾸는 데는 이유가 있다. 표지가 대기 중일 때 깊이가 K 아래로 내려갔다고 일반 MESSAGE로 넣으면, 표지가 나중에 더 새 값을 먼저 내보내고 그 뒤에 더 오래된 MESSAGE가 나간다. `src/hub/tests.rs`의 `a_pending_marker_takes_new_values_even_below_the_depth`가 이 경우를 본다. 깊이를 먼저 보도록 분기 순서를 바꾸면 이 테스트가 `a:m4, a:m3` 순서를 받아 실패한다.

실제 gateway는 위와 같은 조건(연결 1,000개, 탐침 50개, 종목 3개, 워밍업 3초, 측정 10초)으로 쟀다. 한 회차 안에서 종목당 건수마다 기본 정책과 K=8, 64, 256을 차례로 돌렸고, 이렇게 세 회차를 돌렸다. 모두 `--metrics`를 줬다. 2026-11-20 21:12~21:21에 같은 기계에서 load average 4.9~6.9일 때 쟀다. 결과 파일은 `bench/results/slow-policy-k-off-*.json`, `slow-policy-k{8,64,256}-*.json`이고, K=0은 위 표(`slow-policy-on-*.json`)를 그대로 비교 기준으로 쓴다.

K=64와 K=256은 9번 모두 탐침 유실과 건너뜀이 정확히 0이었다. K=8은 초당 80건의 두 번째 회차에서 57건을 건너뛰었고(큐에 넣은 MESSAGE 약 299만 건 대비 0.002%), 탐침이 118,100건 가운데 1건을 받지 못했다. 표에서 그 회차의 두 칸은 반올림해서 0으로 보이지만 0이 아니다. K=8의 나머지 8번은 0이었다.

같은 조건에서 K=0은 0.5~19.0%를 잃었다. 지연과 CPU는 기본 정책과의 차이가 실행 사이의 흔들림보다 작았다. 9번 모두 0이었던 가장 작은 측정값은 64이고, 8과 64 사이의 K는 재지 않았다.

이 36번에서는 기본 정책도 끊긴 연결이 없어 과부하가 생기지 않았다. 종목당 초당 160건으로 과부하를 만들려 했지만, 그 조건에서는 gateway가 끊지 않은 연결까지 수백 개씩 끊겼다. 커널의 네트워크 메모리 요청 거절(`netstat -m`의 `requests for memory denied`)도 160건 한 번에 272건 늘었고, 같은 방법으로 돌린 80건 한 번에서는 늘지 않았다. 측정 환경의 한계가 섞였으므로 160건 결과(`slow-policy-k*-160-*.json`)로는 K를 판단하지 않는다. 실제 gateway가 과부하일 때 K 변형이 어떻게 되는지는 재지 못했다.

예제의 K 줄은 위 표들과 같은 예제를 다시 세 번 돌려서 얻었다(2026-11-20 21:26~21:40, load average 4.9~12.4). 같은 실행의 K=0과 지금 방식을 함께 적는다. 두 번째 실행은 기계가 바빠 모든 방식이 느렸다.

| 연결 | 방식 | 정상 경로 p50 us | CPU us/건 |
| --- | --- | --- | --- |
| 1,000 | 지금 | 168.9, 291.6, 166.9 | 656, 1,000, 654 |
| 1,000 | K=0 | 183.5, 348.8, 221.1 | 750, 1,254, 906 |
| 1,000 | K=64 | 172.1, 311.9, 203.8 | 660, 1,100, 784 |

| 10,000 | K=64 | 1,706, 2,024, 1,933 | 6,995, 8,440, 7,995 |

정상 경로에서 K=64는 세 실행 모두 K=0보다 p50과 CPU가 작았다. 지금 방식과 견주면 연결 1,000개에서는 세 실행 모두 p50이 2~22% 길었고, 10,000개에서는 -12~+4.5%로 방향이 섞였다. 코드에서 읽으면 K=64는 발행마다 칸 잠금 한 번과 깊이 읽기 한 번을 더 하지만, 표지를 만들고 쓰는 쪽이 칸을 다시 잠가 꺼내는 일은 없다. 어느 쪽이 얼마를 쓰는지 나눠 재지는 않았다.

멈춘 수신자에서 K=8은 세 실행 모두 quiet과 가장 오래된 hot 7건을 받은 뒤 최신 hot을 받았다(프레임 9개, 붙든 본문 2,232B). K=64는 오래된 hot 63건 뒤에 최신을 받았다(프레임 65개, 16,120B). 위의 계산 방식으로 붙든 메모리는 K=8이 2,688B, K=64가 18,816B다. 둘 다 quiet을 받았고 연결은 유지됐다. 오래된 hot이 K보다 하나 적은 것은 먼저 들어간 quiet이 깊이 하나를 차지했기 때문이며, 이 프레임 수는 구독 둘에 quiet을 한 번만 발행한 이 조건의 값이다.

밀린 수신자의 유실률(%, 세 실행의 중앙값)이다. 예제는 유실률을 소수 첫째 자리까지 출력하므로 표의 0은 0.05% 미만이라는 뜻이다. 같은 실행의 지금 방식은 초당 120건 2.0배(28.0%, 끊김)와 80건 2.0배의 한 실행(2.2%, 끊김)을 빼고 모두 0.0이었다.

같은 실행의 지금 방식은 2.0배에서 p50이 2,891~4,815ms였다. K=8은 초당 80건 0.5배의 한 실행에서 9.9%를 잃었는데, 그 실행에서는 K=0도 30.1%를 잃었다. 초당 5건 2.0배의 K=64는 8초 동안 쌓인 양이 깊이 64를 크게 넘지 못해 유실이 적고 지연이 길다.

처리 시간이 발행 간격의 0.9배일 때까지 K=64는 세 실행 모두 유실률이 0.0으로 출력됐고, K=8은 종목당 건수별 중앙값으로 2.5~3.2%를 잃었다. 1.1배에서는 큐가 K를 넘으면서 K=64도 5.8~8.4%(초당 40건 이상)를 잃었다. 2.0배면 처리할 수 있는 양이 절반이라 어느 K든 절반 가까이 잃는다. 그때 p99 지연은 대략 K x 처리 시간이었다. 초당 120건 2.0배에서 계산하면 K=8은 44ms, K=64는 356ms이고, 관측한 p99는 44.3ms와 353.8ms였다.

불변식 검사에 K=8을 더했다. 세 실행 모두 assert에 걸리지 않았다. 끊긴 라운드는 1, 1, 0이고, 버린 MESSAGE는 100,898~101,576건, 끝까지 살아 있는 최신 우선 구독 가운데 마지막 발행분을 못 받은 구독은 0/50, 0/55, 0/56이었다.

리뷰에서 예제의 측정 코드를 고친 뒤 한 번 다시 돌렸다(2026-11-21, load average 5.7~7.2). 고친 것은 발행 시각을 첫 방식에 넣기 전에 재기, 측정 구간을 넘긴 마지막 발행 빼기, `DepthTx`가 칸 확인과 교체를 한 번에 잠그기, 고리가 RECEIPT를 넣으려고 버린 MESSAGE도 세기, 끊긴 라운드에서도 큐가 받은 RECEIPT를 모두 받았는지 보기다. 위 표들은 고치기 전 세 실행의 값이고 다시 재지 않았다. 다시 돌린 한 번에서 assert는 걸리지 않았고, 멈춘 수신자의 K=8과 K=64 프레임 수와 본문 바이트는 위와 같았다. 밀린 수신자에서 0.9배까지 K=64의 유실은 모두 0.0이었고 K=8은 3.3~3.6%로 위 중앙값보다 조금 컸다. 1.1배의 K=64는 초당 40건 0.0%, 80건 9.3%, 120건 6.9%였고, 초당 120건 2.0배의 p99는 K=8 44.1ms, K=64 352.9ms였다. 정상 경로의 연결 10,000개에서 K=64의 p50은 지금 방식보다 5.4% 길어 위에 적은 범위(-12~+4.5%)를 벗어났다.

기본값은 64로 정했다. 실제 gateway에서 9번 모두 유실과 건너뜀이 0이었던 가장 작은 측정값이 64다. K=8은 초당 80건에서 한 번 건너뛰었고, 예제에서 처리 시간이 발행 간격의 0.9배인 연결도 K=8에서는 중앙값 2.5~3.2%를 잃었다. 같은 조건에서 K=64는 0.0이었다. K는 송신 큐에서 병합을 시작하는 깊이다. 64로 두면 최신 우선 topic만 구독한 멈춘 연결이 붙드는 대기분은 송신 큐 용량 1,024건 대신 일반 MESSAGE 64건과 구독당 표지 1건이다. 풀린 연결이 어느 구독의 최신을 받기 전에 먼저 받는 오래된 체결(최신 우선 topic의 일반 MESSAGE)도 최대 64건이다. 일반 MESSAGE는 큐에 K건 미만이 쌓여 있을 때만 들어가기 때문이다. 다만 그 앞에 다른 구독의 표지와 RECEIPT가 더 있을 수 있어 먼저 받는 프레임 수는 64를 넘을 수 있고, 같은 연결의 끊기 정책 topic MESSAGE는 K와 상관없이 큐가 찰 때까지 쌓인다. 256도 실제 gateway에서 9번 모두 0이었지만, 대기분과 먼저 받는 오래된 체결의 상한이 네 배로 는다.

### 읽을 때 주의할 것

소켓 쓰기, 웹소켓 프레임 조립, 쓰기 묶음(`src/connection/batch.rs`)이 빠져 있다. 정상 경로의 차이는 hub와 큐에서 생기는 차이뿐이다.

밀린 수신자의 처리 시간은 일정한 값이다. 실제 느린 클라이언트는 TCP 창과 상대의 수신 속도에 따라 몰아서 풀린다. 이 측정은 macOS 한 기계에서만 했고 Linux 가상 머신에서는 하지 않았다.
