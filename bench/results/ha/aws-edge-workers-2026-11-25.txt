## edge 컨테이너의 CPU와 메모리

5초마다 gateway Pod의 edge 컨테이너에서 /proc/[pid]/stat의 utime+stime(CLK_TCK 100)과 cgroup의 memory.current, memory.peak, cpu.stat usage_usec를 읽었다. worker core는 연속한 두 표본의 tick 차이를 시간으로 나눈 값이고, 표에는 구간의 중앙값을 적었다. worker 2개일 때 primary 프로세스의 중앙값은 모든 구간에서 0.01 core 미만이었다. worker 1개일 때는 primary 없이 프로세스 하나가 연결을 받는다. 프로세스 합계와 cgroup의 구간 중앙값은 1% 안에서 같았다. memory.peak는 컨테이너가 시작된 뒤의 최댓값이라 같은 Pod의 앞 실행 값을 포함한다. 차단 실행에서는 차단된 b Pod에 대한 exec가 시간 제한을 기다리느라 표본 간격이 약 70초로 벌어져 표본이 2개뿐이다.

## AZ b 서브넷 차단 (aws-az-isolate-1000-2workers.json)

배치는 종료 실행과 같다. 시작 때 a 296, b 344, c 360.
차단 09:23:48, 해제 09:26:49.
gateway a: 09:23:49.285 Degraded, 09:24:04.985 Ready. gateway c: 09:23:49.332 Degraded, 09:24:05.040 Ready. gateway b: 09:23:49.190 Degraded, 09:26:55.490 Ready.
NLB target: a와 c 09:23:54 draining, 09:24:10 initial, 09:24:37 healthy. b 09:24:26 unhealthy, 09:24:31 draining, 09:27:00 initial, 09:27:32 healthy.
active feed는 재시작하지 않았고 lease holder가 바뀌지 않았다.
gateway별 연결 수: 차단 0초 a 296 c 360, 60초 a 507 c 493, 이후 측정 끝까지 같았다. 표본 간격이 60~70초라 그 사이의 변화는 남지 않았다.
gateway가 스스로 끊은 연결(종료 실행 끝의 누적값과의 차이, 두 실행 사이에는 클라이언트가 없었다): a source-stale 1, c source-stale 5, b heartbeat-timeout 344. edge의 10초 집계로 a의 1건은 09:23:47~57, c의 5건은 09:23:45~55에 났다. 클라이언트가 기록한 연결 종료는 receive-deadline 344와 source-stale 6뿐이다(rejected-503과 connect-aborted는 접속 실패다). 차단된 b의 클라이언트는 frame을 받지 못하므로 source-stale로 끝날 수 없고 b의 344개는 모두 끊겼으므로, receive-deadline 344는 b의 344개가 하나씩 차지한다. 따라서 a와 c의 기존 연결 중 끊긴 것은 많아야 6개다. 09:23:57 뒤로는 측정을 마치며 연결을 닫을 때(c 09:33:05)까지 a와 c에서 upstream_closed, client_closed, relay_error가 없었다. 6건에 차단 뒤 다시 붙은 연결이 섞였는지는 연결별 기록이 없어 가리지 못했다.
edge: a upstream_unavailable 896, c upstream_unavailable 891. 합 1,787은 클라이언트가 받은 rejected-503 1,787건과 같다. Degraded인 동안 a와 c가 새 연결을 거절한 것이다.
