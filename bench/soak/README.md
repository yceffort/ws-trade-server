# 복합 수명 검증

인증, 제한, WSS와 압축, heartbeat, 스냅샷, 메트릭과 구조화 로그를 함께 켜고 반복 연결과 실패 복구를 확인한다. 합성 feed와 임시 토큰, 자체 서명 인증서만 사용한다. 기존 `loadgen`의 지연 및 전달률 벤치와 별도로 실행한다.

```sh
cargo build --locked --release --bins
npm ci --prefix edge
node bench/soak.mjs --seconds 600 --cycles 6 --connections 40 --out bench/results/soak-local.json
```

Node 22 이상, OpenSSL, `ps`가 필요하다. 저장소 루트에서 실행한다. `--seconds`는 워밍업과 복구 시간을 제외한 유지 시간의 합이다. 기본값은 600초, 6회, 40개 연결이고 상한은 각각 1800초, 20회, 200개다. `--seconds`는 회차 수 이상이어야 한다. `--bin-dir`로 이미 빌드한 gateway/feed 경로를 지정할 수 있다. 환경 값, 원본 토큰과 체결 본문은 결과에 저장하지 않는다.

첫 회차는 워밍업이다. 이후 회차마다 정상 클라이언트를 WSS로 연결하고 두 topic을 구독한다. permessage-deflate 협상, MESSAGE의 연결별 연속 순번과 본문 바이트 수, JSON 형식과 각 유지 구간의 수신 진행을 확인한다. 일부 토큰을 폐기해 활성 세션이 종료되는지 확인하고, 복구 후 재접속 및 재구독한다. 정상 연결의 절반도 매 회차 새 연결로 바꾸고 스냅샷을 조회한다. 중간 회차에는 feed를 재시작해 메트릭의 seq 리셋과 데이터 수신 복구를 확인한다.

별도의 평문 WS 연결 하나는 읽기를 멈춘 뒤 구독 한도를 넘긴다. 서버의 연결 수가 3초 안에 줄어드는지 확인한 후 다시 읽어 오류 사유를 검사한다. 이 조건이 모든 OS에서 커널 송신 버퍼 포화까지 유발한다는 뜻은 아니다. 쓰기가 반드시 막힌 상태의 1초 거절 종료는 Rust의 작은 양방향 파이프 테스트에서 별도로 검증한다.

유지 구간에는 약 1초마다 gateway의 RSS와 메트릭을 읽는다. 매 회차 뒤 모든 연결을 닫고 연결 수, 구독 수, 송신 큐가 0으로 돌아오는지 확인한다. 워밍업 뒤의 유휴 RSS를 기준으로 이후 유휴 RSS가 기본 64 MiB 이상 늘면 실패한다. 이 허용량은 `--rss-growth-mib`로 바꾸며 보편적인 누수 판정 기준이 아니다. allocator가 반환하지 않은 메모리도 RSS에 남는다. peak는 표본 중 최댓값으로 짧은 순간의 증가를 모두 잡지 못한다.

출력 JSON에는 실행 조건과 커밋, OS 및 Node 버전, 관측 표본, 회차별 유휴 상태, 누적 수신 수, 인증 폐기 및 재접속과 feed 재시작 횟수, JSON 로그 이벤트 수를 남긴다. 정상 수신의 순번 누락, 예상 밖 종료, 링 유실, 디코딩 실패, 자원 미반환 또는 RSS 한도 초과 시 종료 코드가 0이 아니다. 종료 신호와 실패에서도 생성한 클라이언트, 프록시, 자식 프로세스와 임시 디렉터리를 정리한다. 정리 중 오류도 결과에 남긴다.

일반 CI는 4개 연결과 2회차, 6초 유지 시간으로 회귀를 확인한다. GitHub Actions의 `Combined soak`는 수동 실행이며 결과 JSON을 14일간 보관한다. 실행 시간 제한은 40분이다. 단일 호스트의 수 분 실행으로 장기간 누수 부재, 다중 인스턴스 장애 전환이나 운영 용량을 보증하지 않는다.
